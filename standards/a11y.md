# Accessibility

Accessibility is a contract with external, normative specs, not a feature
to be invented per component. The W3C web accessibility specs are the
baseline for every interactive behavior, including behaviors that never
touch a browser, because they are the only stable, machine-mapped definition
of what a widget is and what a user may expect from it. A senior holds the
API to those specs, looks them up rather than recalling them, and treats a
disagreement between the API and a normative spec as a bug in the API until
someone writes down why not.

## Core

- **Roles, states, properties.** WAI-ARIA gives every widget a role and a
  vocabulary of states and properties. The role decides what the user is told
  it is; the states decide what they are told about it now. A behavior model
  that emits ARIA terms can be translated to any platform's accessibility
  API, because Core-AAM already maps them.
- **Accessible name and description.** Every interactive element resolves a
  name through a fixed algorithm, Accname: `aria-labelledby`, then
  `aria-label`, then content or a native label. An element without a
  resolvable name is announced as nothing. Names are text, never icons.
- **Keyboard contract.** Everything a pointer can do, a keyboard can do.
  Focus moves in a predictable order, is always visible, and never gets
  trapped except by a modal that owns it on purpose and releases it. The APG
  patterns document the expected keys per widget.
- **Focus management.** Opening a dialog moves focus in; closing it returns
  focus to the trigger. Removing the focused element moves focus somewhere
  sensible, not to the document body. Siblings of a modal are inert.
- **Announcements.** Dynamic changes that a sighted user sees are announced
  through live regions or the platform's notification service. Polite for
  updates, assertive only for things that cannot wait.
- **WCAG's four principles.** Perceivable, operable, understandable, robust.
  Success criteria are the bar; level AA is the common target. WCAG2ICT
  carries the technology-independent criteria to non-web software, which is
  why a native or terminal surface is held to WCAG at all.
- **Platform obligations are additive.** Touch target size, gestures,
  hardware Back, VoiceOver and TalkBack idioms come from Apple, Android, and
  React Native guidance. They add to the web contract; they never contradict
  it.
- **Automated checks have a ceiling.** They catch missing names and invalid
  attributes. They do not catch a focus order that makes no sense or an
  announcement that misleads. Those need a citation and a human.

## Checks

- Every interactive element resolves a non-empty accessible name through
  Accname, and the name is text.
- Every widget has the role the spec gives that widget, and its states track
  the behavior in real time.
- The keyboard contract matches the APG pattern for that widget, or the
  deviation is written down next to the API.
- Focus is visible, moves in a sensible order, enters and leaves modals
  correctly, and never lands on the body after a removal.
- A dynamic change a sighted user would notice is announced, with the right
  politeness.
- Where the API and a normative spec disagree, a justification exists in the
  package's spec. If not, the API is the bug.
- On a non-web surface, every ARIA term is mapped, overridden with a recorded
  reason, or recorded as dropped. Nothing is silently skipped.
