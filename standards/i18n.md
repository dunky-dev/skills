# Internationalization

Internationalization, i18n, is the engineering that lets one build serve any
locale: no string, format, direction, or sort order is baked in.
Localization, l10n, is the later act of adapting that build to one locale:
translating the strings, choosing the formats, checking the culture. They
are not the same. i18n is done once, by the people who write the code; l10n
is done per locale, by people who may never see the code. A senior treats
i18n as architecture: a locale-dependent decision made in code is a bug,
even when it happens to be right for the author's locale.

## Core

- **Strings are data.** Every user-facing string lives outside the code
  behind a stable key. No concatenation: "You have " + n + " items" cannot
  be translated because word order and agreement differ per language. Whole
  sentences with placeholders, always.
- **Plurals and gender are not two forms.** Languages have from one to six
  plural categories, zero, one, two, few, many, other, and the rules come
  from CLDR. ICU MessageFormat expresses plural, select, and nested variants
  in one message. A hand-written `n === 1 ? 'item' : 'items'` is wrong in
  most of the world.
- **Formatting belongs to the locale.** Dates, times, numbers, currencies,
  units, lists, and relative times are formatted by the platform's locale
  data, the `Intl` family in JavaScript, never by string manipulation.
  Collation, meaning sort order, is locale-dependent too: ä sorts
  differently in Swedish and German.
- **Direction.** Arabic, Hebrew, Persian, and Urdu are right-to-left. Layout
  uses logical properties, start and end, not left and right. Mixed-direction
  text needs bidi isolation or numbers and punctuation jump. Icons that imply
  direction, arrows and progress, mirror.
- **Text expands.** German and Finnish run about 30% longer than English;
  CJK runs shorter but taller. Fixed-width containers, truncation, and
  all-caps styling break under translation. Pseudo-localization, inflating
  and accenting every string, finds these before any translator does.
- **Unicode is not ASCII with extras.** A character is not a code unit, a
  grapheme cluster is what the user sees as one character, and length,
  truncation, and reversal must respect it. Casing is locale-dependent, the
  Turkish dotless i being the classic failure. Normalize before comparing.
- **Locale is negotiated, not assumed.** BCP 47 tags, `pt-BR` not `pt`,
  with a fallback chain. The user's choice beats the browser's beats the
  system's. Time zone is separate from locale and separate from language.
- **Input and output are both localized.** Decimal separators, date order,
  and keyboard methods differ. A form that parses "1,5" as fifteen hundred
  has an i18n bug, not a validation bug.

## Sources

| Source                                                                                            | Status    | What we take from it                                                  |
| ------------------------------------------------------------------------------------------------- | --------- | --------------------------------------------------------------------- |
| [Unicode CLDR](https://cldr.unicode.org/)                                                         | Living    | The locale data everything else formats with: plurals, dates, names.  |
| [ECMA-402 Intl](https://tc39.es/ecma402/)                                                         | Standard  | Locale-aware formatting, collation, plural rules, segmentation in JS. |
| [ICU MessageFormat](https://unicode-org.github.io/icu/userguide/format_parse/messages/)           | Living    | One message syntax for plurals, select, and nesting.                  |
| [BCP 47 / RFC 5646](https://www.rfc-editor.org/rfc/rfc5646)                                       | Standard  | Language tags and matching.                                           |
| [UAX #9 Bidi](https://www.unicode.org/reports/tr9/)                                               | Standard  | How mixed-direction text lays out and why isolation is needed.        |
| [UAX #29 Segmentation](https://www.unicode.org/reports/tr29/)                                     | Standard  | Grapheme clusters, words, sentences. What "one character" means.      |
| [W3C i18n](https://www.w3.org/International/)                                                     | Articles  | Practical guidance on direction, text expansion, language markup.     |
| [MDN Intl](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl) | Reference | The platform API surface and its browser support.                     |

## Checks

- No user-facing string is a literal in code; every one has a key and a
  message with placeholders, not concatenation.
- Every count in a message uses plural rules, and every message with plural
  or gender variants is one ICU message.
- Dates, numbers, currencies, lists, and relative times go through locale
  formatting; nothing is built with `toString` and string joins.
- Layout uses logical properties; directional icons mirror under RTL; mixed
  text is bidi-isolated.
- Containers survive 30% longer strings and taller glyphs without clipping or
  overlap; pseudo-localization passes.
- String length, truncation, and comparison operate on grapheme clusters and
  normalized text.
- The locale comes from a negotiated BCP 47 tag with a fallback chain; time
  zone is handled separately.
